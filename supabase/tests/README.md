# Attendance verification

`attendance_preflight.sql` is read-only and returns function definitions, policies and column metadata only. Compare its output with `004_attendance_hardening.sql` before approving production application. In particular, an existing roster function with different output columns requires a separate migration design: do not drop it blindly.

004 replaces two role helpers, the roster RPC, confirmation RPC, and the new-user trigger function. It restricts EXECUTE to authenticated for the helper/RPC functions. It neither changes existing profile roles nor writes event responses during application. Confirmation of actual attendance is limited to event dates in Asia/Tokyo; undo remains available afterwards. No LINE call is added. Existing production definitions may have diverged from the repository: preserve any additional rules after comparison.

Local verification uses PGlite (real PostgreSQL via WASM), an in-memory database and synthetic CODEX_TEST data. The application dependencies do not need modification. Install the test runtime in a temporary directory:

```sh
npm install --prefix /tmp/office-visit-db-tests --cache /tmp/office-visit-npm-cache --no-save --package-lock=false @electric-sql/pglite
PGLITE_MODULE=/tmp/office-visit-db-tests/node_modules/@electric-sql/pglite/dist/index.js node supabase/tests/security.mjs
```

The fixture loads schema.sql, 002, 003, 004, 005, 006, 007 and 008, replaces Supabase Auth with a local auth.users/auth.uid() fixture, omits pgcrypto extension setup (built-in gen_random_uuid is available) and Realtime publication commands, and models the event-table SELECT grants reported in the handoff. It does not connect to production or model the reported custom is_event_member policy. Passing local tests does not establish production SQL parity or Supabase API/Realtime permissions.

67 assertions cover: new accounts ignoring a supplied admin role, denial for member/inactive/missing-profile/unauthenticated calls, key-manager creation denial, other members' reservation/membership/response invisibility, roster inclusion of unanswered members, admin/key-manager confirmation and undo persistence, planned time preservation, absent/unanswered/null/future-date rejection, anon execution denial, Zoom response saving, other users' reservation update denial, reservation creation/readback, key-manager opening, admin event creation with membership, venue response acceptance when venue_allowed, venue response rejection when venue_allowed is false, venue and Zoom rejection when office_required is true, venue attendance confirmation, rejection of a response change after attendance is confirmed, response changes allowed again after a manager undoes confirmation, roster row count for a venue event, empty-reason rejection for cancel/edit, other users' cancel denial, edit with reason recorded in reservation_audit_logs, cancel with reason recorded and status set to cancelled, a cancelled reservation no longer blocking a new one at the same time, delete_reservation now denied even for the owner (EXECUTE revoked), a member reading zero audit rows (RLS-filtered, not an error), key-manager/admin reading the audit rows for a reservation, anon denial on the audit table, member denial on record_event_response_via_service, the service-role path defaulting office arrival to the event start time, office_required blocking Zoom through the service path too, venue acceptance through the service path, member denial on event_notification_targets/event_report_recipients/log_notification, and key-manager/admin reading notification targets and writing notification_logs (which had no INSERT policy at all before 008).
